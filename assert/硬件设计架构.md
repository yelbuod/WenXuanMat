# 硬件设计架构

## 部分松耦合

分为几点原因

1. xuantie matrix 指令集存在部分需要写入rd的指令, 因此如果在具备重命名技术的处理器上进行扩展, 例如C910, 就必须经过其IR阶段的重命名逻辑, 为指令rd分配物理寄存器. 后续可能可以优化, 例如只为需要写入GPR的指令进入IR stage并分配物理寄存器, 其他的直接发送到matrix entries.
2. 编译工具链编译结果存在普通指令和矩阵指令混用, 因此如果采用完全解耦的方式, 预估效率可能较低.

## 异常指令处理

可能引发异常的指令:

1. Matrix Size Configuration的`sizeK` 如果不是`element size in byte`的整数倍则引发**非法指令异常**.
   但是是先配置`sizeK`才会有后续ALU/LSU指令内包含关于`element size`的配置? **这应该如何判断?**
2. 定义在`mstatus`, 影射在`sstatus`, 与`FS/VS/XS`类似的, 表示矩阵指令集状态的`MS`位域, 如果在设置为`2'b00(All off)`时执行任意矩阵指令和访问任意矩阵CSR时会引发**非法指令异常**.
3. `fcsr`的浮点dynamic rounding mode设置为无效值, 则任意带dynamic rounding mode的浮点操作会引发**非法指令异常**.
4. 定义在`mstatus`的表示浮点状态的`FS`如果设置为`off`, 任意矩阵浮点指令的执行会引发**非法指令异常**.
5. 浮点运算相关会引发**无效操作异常**.

2/3/4都可以在译码阶段触发异常? 但是又要考虑前面有预测中的分支指令?

## 记分牌架构方案

拟定记分牌(scoreboard)架构方案为矩阵执行流水线的主架构方案, 分析如下:

1. xuantie矩阵指令集编译的workload存在矩阵指令与普通指令混用, 矩阵指令分布稀疏; 矩阵指令间的相关性依赖少等特点, 刚好弥补了scoreboard方案(由于不支持重命名技术)在指令存在相关性依赖的情况下阻塞的缺点.

2. 另外, 可以利用**软件workload**的特性和**顺序发射无法"背靠背"发射**的特性, 适当增加scoreboard架构所需的"功能部件寄存器", "执行信息寄存器", "写回寄存器"等资源.

   > 可能无需利用"背靠背"特性, 可以利用lch fail stall组织会因latch fail影响顺序发射的情况, 并且"背靠背"发射后仍可利用流水满足矩阵配置与执行的"背靠背"匹配. 即执行可以用上最新的依赖的配置.

## 矩阵编程模型

硬件: 拟定RLEN=512 (spec数据分析使用的最大RLEN值), 但尽量在设计时写成可配置的形式便于后续修改. 并且目前来看, **软件workload的运行不依赖这个常量RLEN**.

## 矩阵CSR

* xmrstart: URW权限, 用于指示matrix load/store**起始的row索引**.一般**由matrix load/store指令产生的trap来写入修改**: 意思是当矩阵访存出现trap时, 需要进入异常服务程序, 即trap handler, 中断访存执行, 此时记录被中断的矩阵访存指令操作进行到的row的索引, 这样从trap恢复执行之后, 就可以借助trap时写入的xmrstart寄存器, 从产生trap时被中断的row继续执行访存. 在任意矩阵指令执行完毕后会恢复到0.
* xmcsr: URW权限, 保存了**定点**(?)操作的"saturation flag"和"rounding mode"
* xmsize: URW权限, 由矩阵配置指令(mcfg)写入, 主要用于指示矩阵指令操作的矩阵大小.
* xmlenb: URO权限, matrix register size in byte, **常数**, =mrows*xrlenb, mrows=RLEN/32, xrlenb=RLEN/8
* xrlenb: URO权限, RLEN in bytes, **常数**, =RLEN/8
* xmisa: URO权限, 用于指示支持的矩阵运算格式

**在demo程序中, 仅有xmlenb和xrlenb被使用, 因此暂时先支持这两种只读的常数CSR寄存器**, 并根据上一节提到的RLEN=512设置正确的值.
